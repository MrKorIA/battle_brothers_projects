## Жёсткое правило API

**Запрещено выдумывать функции, константы и сигнатуры.** Каждое использование незнакомого метода/константы
сначала проверяется по источникам: распакованная ваниль `Z:\GameMods\Battle Brothers\mods\!project\data_014`
(grep по определениям) либо данный пользователем референс. Если подтвердить нельзя — не использовать,
а спросить или перестроить решение на проверенном API. Проверенные ловушки (полный список — в
`docs/locations/tactical_location_guide.md`): `Const.EntityType.Donkey` не существует (есть `CaravanDonkey`);
у тайла нет `hasObject()`; скилловый `onDamageReceived(_attacker, _damageHitpoints, _damageArmor)` ничего
не возвращает; у `CombatInfo` обязателен `TerrainTemplate`; `fillVisibility(Player, true)` — отключение
тумана войны; `Navigator().teleport()` в фазе развёртывания — мёртвая блокировка (игрока расставлять
`addEntityToMap`, паттерн tutorial_contract); **Squirrel BB не поддерживает битовые составные присваивания** (`|=`, `&=`, `^=`, `<<=`, `>>=`) — ваниль пишет `a = a | b`, иначе парсер падает с «expression expected»); мод `mod_useful_pack` (`mod_crisis_duration_setting`) полностью переписывает `updateGreaterEvil` на уровне инстанса — классовые хуки на него молча в тени; лечится мягкой сортировкой `queue(">mod_crisis_duration_setting", ...)` + обёрткой через `mods_hookNewObject` (хуки применяются к инстансу в порядке регистрации, см. `mod_hooks/!!redirect.nut`), реакции на смену состояния — хуком `update` + флаги `World.Statistics.getFlags()`); обёртки modern hooks обязаны повторять сигнатуру оригинала включая параметры по умолчанию (`function update(_ignoreDelay = false)`, а не `update()`), иначе падение «fewer total parameters» при загрузке; тот же класс падений — `q.X = @(__original) {...}` по функции, которой НЕТ в классе/предках («failed to set function ...: there is no function to set»): modern hooks требует существующий оригинал, НОВЫЕ члены объявляются только через `q.X <- {...}` (урок: перенос contract-хука Reforged, где `getSecondsRequiredToTravel` — новый метод ванильного класса, в ванили её нет — инлайн внутри `getDaysRequiredToTravel`); `assignRandomEquipment` движком НЕ вызывается — только явно (`tactical_entity_manager.spawnNewEntity` для отрядов с карты мира, контракты/ивенты руками), голый `Tactical.spawnEntity` в событиях/объектах экипировку не раздаёт (лечение: вызов из конца `onInit` юнита — повторный вызов безвреден, методы обычно защищены `hasEmptySlot`; слепой вызов на юните без такого метода падает с «index does not exist»); из состояний/экранов контракта (их таблицы, `this` = Table) `this.new` недоступен, а `this.Contract.new(...)` падает с «the index 'new' does not exist» (подтверждено логом игры; `new` резолвится только на `this` методов инстанса) — создавать объекты из стейта/скрина через метод инстанса контракта: `this.Contract.myMethod()`, внутри которого обычный `this.new(...)`; скриптованный бой с пустым `CombatInfo.Entities` молча не стартует — `showCombatDialog` считает `hasOpponents` по этому списку и при нуле просто выходит (`world_state.nut`), ошибки в логе нет, врагов спавнить в `BeforeDeploymentCallback` при этом поздно — начальный гарнизон обязан быть в `Entities`, а вот записи `Entities` движок сам экипирует (`setupEntity`: `assignRandomEquipment`, фракция из поля `Faction`, поле `Callback` на записи — точка для кастома, паттерн `raze_attached_location_contract.nut`; следить за `Variant` — у части troop-таблиц он >0, и тогда КАЖДЫЙ боец станет минибоссом); итоговые экраны контракта после боя показывать из `update()` по флагам, которые ставят `onCombatVictory`/`onRetreatedFromCombat` (паттерн free_greenskin) — прямой `setScreen`+`showActiveContract` из них всплывает ещё в тактике и ломается на карте; конец боя считается по `isNoCombatantsLeft` — только не-`IsNonCombatant` враги держат бой, поэтому объекты-цели (бочки и т.п.), которые должны удерживать поле, спавнить с `m.IsNonCombatant = false` на инстансе (не трогая класс-зависимость); эффект на броне/предмете (тултип + механика, живущие пока предмет надет) вешается override `onEquip()` предмета + `this.addSkill(this.new("scripts/skills/effects/..."))` — паттерн ванильного оружия (`fighting_spear.nut`), переживает сейв/лоад (SkillPtrs не сериализуются, при десериализации предметы переэкипируются). ОБЯЗАТЕЛЬНА симметричная явная снятка: override `onUnequip()` с удалением эффекта по ID + `skill.getItem() == this` через `removeSelf()` — полагаться на `clearSkills()`/`SkillPtrs` НЕЛЬЗЯ: `removeFromContainer()` (передача лута вне unequip) обнуляет контейнер без `onUnequip`, и эффект остаётся на актёре навсегда — для эффектов с апгрейдом в `onCombatFinished` это эксплойт (апгрейд срабатывает без брони/чужой брони); эффект дополнительно проверяет `getItem().getContainer() == getContainer().getActor().getItems()` перед манипуляцией предметом; в `onCombatFinished` скилла скилл-контейнер находится в IsUpdating — `Skills.remove()` в это время молчаливый no-op, `add()` уходит в отложенный SkillsToAdd, снять скилл можно только `removeSelf()`; замена экипированного предмета (unequip + equip нового) внутри onCombatFinished безопасна — контейнер сам применит мутации после итерации (образец: `mod_Skaven_faction/scripts/skills/effects/warp_shard_upgrade_effect.nut`); `armor.nut`/`helmet.nut` переопределяют `isDroppedAsLoot()` с порогами прочности (у врага — >30 и ≥25%) — гарантированное выпадение разрушенной вещи даёт флаг `ItemType.Named` (у Named-вещей врага условия прочности нет).

## Инструменты

- `tools/sprite_editor.html` — локальный визуальный редактор координат спрайтов brush (файл
  `metadata.xml` из распаковки `bbrusher.exe unpack`): сборка куклы (голова+тело+прочее) на белой
  сцене из общего pivot, drag/стрелки/поля для left/right/top/bottom/offsetX/offsetY, запись
  изменений обратно в metadata.xml. Основной вход — «Открыть PNG…»: 1-й диалог PNG, 2-й диалог
  ЕГО xml-файл (handle даёт координаты И запись при сохранении; картинка из PNG; левая панель
  показывает ТОЛЬКО открытое). Привязка png→кисть (pngMap + сверка по ВСЕМ загруженным xml) —
  строго по ИМЕНИ ФАЙЛА картинки (basename img), НЕ по id спрайта: id в brush может не совпадать
  с именем файла (напр. id="bust_head_615" img="entity\heads\bust_head_wushi_02.png" — резолв
  через img). Индекс brush.imgByBase перестраивается и при refreshBrushFromDisk. Диалог xml
  появляется, только если картинка не найдена ни в одной загруженной кисти (textHasImg). При каждом
  совпадении кисть перечитывается с диска (refreshBrushFromDisk; объекты спрайтов обновляются на
  месте, stage не ломается; если по кисти есть несохранённые правки — свежее НЕ подтягивается).
  Файловые диалоги стартуют в папке последнего выбора (startIn = lastPickerLoc, только сессия). Кисти от разных модов живут независимо,
  dirty/buildXml/save раздельные (id могут совпадать!); drag&drop xml+PNG — без записи на диск.
  Отрисовка с z-градацией: тело куклы 0 → доспех 10 → улучшение _back 20 → голова куклы 30 →
  шлем 40 → _front/прочее 60. Слой детали (шлем/доспех/улучшение/оружие) — авто (`armor_up`
  проверять РАНЬШЕ `armor`) + ручной; слой — ВИЗУАЛЬНЫЙ (только z-порядок, НЕ двигает спрайт,
  в XML не пишется; snap-механика удалена целиком). Координаты: у части спрайтов в brush
  края rect'а опущены (только left+top+bottom и т.п.) — отсутствующие края ВЫВОДЯТСЯ из размеров
  PNG (spr._pngW/_pngH при загрузке картинки): оба отсутствуют -> центр на anchor'е, один ->
  известный ± размер PNG. Правки (drag/поля/nudge) пишут display-rect целиком — недостающие
  атрибуты материализуются в XML и добавляются в spr.present (иначе выводка из PNG продолжит
  их игнорировать — спрайт «не двигается по горизонтали»). Запись в XML — setCoordAttr: замена на месте
  (порядок атрибутов сохраняется), дубли вырезаются, парсер при загрузке читает ПОСЛЕДНЕЕ значение дубля.
  «Сбросить» откатывает координаты и spr.present (snapshot origPresent). Куклы по чекбоксам
  (живая/_dead) — `tools/assets/doll_*.png` (ванильные
  bust_naked_body_00 + bust_head_02, НЕ коммитятся, локальные). Чекбокс «тайл» — кукла для
  статичных объектов: `tools/assets/tile_grass.png` (terrain tactical_tiles grass_01) центрируется
  на pivot, объекты object_1 anchor'ятся в его центре — подгонка не нужна.
- **i18n:** словари в `tools/assets/lang_ru.js` / `lang_en.js` (registerLang(code, dict), подключаются
  ДО основного скрипта; ключи — t("key", {param})). Новые пользовательские строки — В ОБА словаря.
  Язык по УМОЛЧАНИЮ — английский (localStorage bbse_lang, null -> en). Переключатель RU/EN в шапке
  (reload). Статика — data-i18n / -tt / -ph.
  ЛОВУШКА: глобальная функция t() — не называть локальные переменные `t` (деструктуризация
  rect'а [l, t, r, b] затеняет и падает с "t is not a function").
- Радиокнопки «шлем/доспех/...» — ВИЗУАЛЬНЫЙ СЛОЙ (только z-порядок, НЕ двигают спрайт, в XML не
  пишутся; авто-угадывание по имени — лишь стартовое значение слоя). Кнопка «На куклу» УДАЛЕНА
  (не востребована; snap-механику вырезали целиком). Ресайз: тянуть жёлтую границу выделенного
  спрайта (edgeHit 6px, resizedRect — визуальный верх = мировой b, кламп мин. размера 1px).
  Кнопки «Копир./Вставить коорд.» переносят шесть координат между вариантами спрайта. Цикл:
  `bbrusher.exe unpack` → редактор → `bbrusher.exe pack`. Проверено: pack/unpack координаты не теряет
  (offsetX="0" пакер сам отбрасывает).
- **Урок buildXml (была бо-бага):** regex из строки с `\\s` матчил буквальную `\s` → замена молча
  падала и координаты ДОПИСЫВАЛИСЬ дублем (XML берёт первое значение — правки не применялись).
  Лечение: `rebuildCoordsInTag` вырезает ВСЕ координатные атрибуты тега и пишет один канонический
  набор (только для dirty-спрайтов; id могут содержать ПРОБЕЛЫ — `"...wushi_ armor16..."`). Дубли
  при загрузке авто-детектятся (parseBrush) и помечаются dirty — одно сохранение чистит файл.
- **Формат координат brush (проверено рендером портрета):** все bust-спрайты висят на ОДНОМ anchor'е,
  мировая ось Y вверх; мировой rect спрайта = (left+offsetX, top+offsetY, right+offsetX, bottom+offsetY),
  PNG ставится в него без поворота (визуальный верх картинки = мировой bottom+offsetY). Y-вниз/«вычитание
  offset» даёт перевёрнутую куклу — НЕ использовать.

## Сборка

- Общая реализация — в корневом `build.sh` (аргументы: `<имя.zip> [каталог мода]`, каталог игры
  можно переопределить через `BB_DATA`). В каждом моде остаётся только тонкий `build.bat`, передающий
  имя zip (см. реестр выше) и каталог мода в общий скрипт. ЗАПРЕЩЕНО запускать сборку
  автоматически — только по явной просьбе пользователя, при закрытой игре (иначе «Corrupted archive»).
- Скрипт упаковывает существующие игровые папки мода (brushes/gfx/music/scripts/sounds/ui + каталог хуков mod_*/zmod_*)
  и кладёт zip с заменой в `Z:\SteamLibrary\steamapps\common\Battle Brothers\data`.
- Сборка с ресурсами — общий `build_brushes.sh` + тонкий `build_brushes.bat` в каждом моде. Алгоритм:
  для каждого `<name>.brush` из `brushes/` мода ищем одноимённый каталог с `metadata.xml` в
  `Z:\GameMods\Battle Brothers\mods\bbros\bin` (есть каталог = спрайты правились в редакторе) →
  `bbrusher.exe pack <bbros>\bin\<name>.brush <bbros>\bin\<name>` (БЕЗ --gfxPath, см. ловушку ниже) →
  копия `<name>.brush` в `brushes/` мода и `<name>.png` в `gfx/` мода (с заменой, gfx создаётся) →
  обычная сборка через `build.sh`. Каталог bbros переопределяется через `BB_BROS`.

## Правила ведения задач

- Текст коммита для вкладки Commit IDE ведём в `.commit-msg.txt` (в gitignore) в корне.
  Туда пишем только содержательное описание фичи/изменений. НЕ пишем туда самоликвидацию:
  то, что агент сам сломал и починил в рамках задачи (например, кавычки/слэши в bat-обёртках).
- Если что-то не получилось с первой итерации и этому есть чему учиться — урок заносим в правила
  (этот файл или профиль мода), а не в текст коммита.
- Генерация .bat через `printf` в git bash: `\\b` в форматной строке съедается как backspace —
  пути с `\bin\` ломаются молча. Писать пути отдельным аргументом через `%s` (либо heredoc).
- **bbrusher pack: НЕ передавать `--gfxPath`.** brush-файл хранит путь к листу (`gfx/<name>.png`),
  и pack резолвит его относительно родителя каталога с brush. Для `<bbros>\bin\<name>.brush`
  дефолт даёт `<bbros>\gfx\<name>.png`. Если передать `--gfxPath <bbros>\gfx`, путь сдвоится
  и png молча улетит в `<bbros>\gfx\gfx\` — мод соберётся со СТАРЫМ png (копия идёт из
  `<bbros>\gfx`). От cwd не зависит.
- Запрещено запускать фоновых агентов (background agents) — работаем строго последовательно:
  один агент за раз, дожидаемся результата. Фоновые агенты на текущий момент нестабильны
  (отвалы по таймауту).
- **Инструменты не должны мусорить в репозитории.** Временные файлы, кэши и профили —
  только вне репо (tmp/каталог инструмента вне git). Урок: браузерная автоматизация
  (Edge/WebView2 через MCP) при открытии `tools/sprite_editor.html` поднимала профили
  (`_prof_<pid>`, `_pp_<pid>`, `_smoke_profile`) прямо в `tools/` — туда попали полные
  юзер-профили Edge (~34 МБ), и IDE-стейджинг тут же подхватил ~800 файлов в git.
  Паттерны добавлены в `.gitignore`; перед `git add -A`/коммитом из IDE проверять
  `git status` на постороннее.
