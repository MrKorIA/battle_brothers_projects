## Жёсткое правило API

**Запрещено выдумывать функции, константы и сигнатуры.** Каждое использование незнакомого метода/константы
сначала проверяется grep'ом по определениям в референс-ванили (`!project/data_014`) или данным
пользователем референсом. Не подтвердилось — не использовать, спросить или перестроить решение.
Все проверенные ловушки (константы, хуки, спавн, onEquip/onUnequip, порт существ в компаньонов AC) —
`docs/api_traps.md`. Ловушки тактических локаций — `docs/locations/tactical_location_guide.md`.

## Тексты (предыстории, события, контракты, кризисы)

- Генерация: `docs/texts/text_generation.md`, `docs/backstories/backgrounds_generation.md` (предыстории),
  `docs/backstories/backgrounds_rules_south.md` (юг), концовки — `docs/backstories/backgrounds_endings.md`
- Проверка — ОТДЕЛЬНЫМ проходом: `docs/texts/text_validation.md`, `docs/backstories/backgrounds_validation.md`
  (формат результата: [OK]/[FAIL] + вердикт)
- Легендарные события — один вариант текста, вариативность не нужна
- Уроки валидации предысторий (сессия вычитки hackflows): файлы hackflows — CRLF + табы,
  многострочный Edit по ним падает — править точечными подстроками без отступов или скриптовой
  заменой (io.open newline='' чтобы не трогать CRLF). Перед тем как править «грамматическую
  ошибку» — перепроверить её grep'ом: была фантомная находка (несуществующее «визиря, посетивший»);
  «наймник» — разговорное, но словарное (не не-слово). `bbros\bin\sq.exe` — рабочий Squirrel:
  соседние строковые литералы без запятых в массивах парсятся (стиль исходника hackflows),
  ваниль так не пишет — запятые проставляем. «алчущие крон» — ванильный RU термин sellswords.
  Одиночный гоблин-всадник — «наездник гоблинов на волке» (по ванильному «волки гоблинов-наездников»).

## Сборка

- Общая реализация — в корневом `build.sh` (аргументы: `<имя.zip> [каталог мода]`, каталог игры
  можно переопределить через `BB_DATA`). В каждом моде остаётся только тонкий `build.bat`, передающий
  имя zip (см. реестр выше) и каталог мода в общий скрипт. ЗАПРЕЩЕНО запускать сборку
  автоматически — только по явной просьбе пользователя, при закрытой игре (иначе «Corrupted archive»).
- Скрипт упаковывает существующие игровые папки мода (brushes/gfx/music/scripts/sounds/ui + каталог хуков mod_*/zmod_*)
  и кладёт zip с заменой в `Z:\SteamLibrary\steamapps\common\Battle Brothers\data`.
- Сборка с ресурсами — общий `build_brushes.sh` + тонкий `build_brushes.bat` в каждом моде. Алгоритм:
  для каждого `<name>.brush` из `brushes/` мода ищем одноимённый каталог с `metadata.xml` в
  `Z:\GameMods\Battle Brothers\mods\bbros\bin` (есть каталог = спрайты правились в редакторе) →
  `bbrusher.exe pack <bbros>\bin\<name>.brush <bbros>\bin\<name>` (БЕЗ --gfxPath, см. ловушку ниже) →
  копия `<name>.brush` в `brushes/` мода и `<name>.png` в `gfx/` мода (с заменой, gfx создаётся) →
  обычная сборка через `build.sh`. Каталог bbros переопределяется через `BB_BROS`.

## Правила ведения задач

- Текст коммита для вкладки Commit IDE ведём в `.commit-msg.txt` (в gitignore) в корне.
  Туда пишем только содержательное описание фичи/изменений. НЕ пишем туда самоликвидацию:
  то, что агент сам сломал и починил в рамках задачи (например, кавычки/слэши в bat-обёртках).
- Если что-то не получилось с первой итерации и этому есть чему учиться — урок заносим в правила
  (этот файл, профиль мода или docs по теме: API-ловушки → `docs/api_traps.md`,
  инструменты → `docs/sprite_editor.md`), а не в текст коммита.
- Генерация .bat через `printf` в git bash: `\\b` в форматной строке съедается как backspace —
  пути с `\bin\` ломаются молча. Писать пути отдельным аргументом через `%s` (либо heredoc).
- **bbrusher pack: НЕ передавать `--gfxPath`.** brush-файл хранит путь к листу (`gfx/<name>.png`),
  и pack резолвит его относительно родителя каталога с brush. Для `<bbros>\bin\<name>.brush`
  дефолт даёт `<bbros>\gfx\<name>.png`. Если передать `--gfxPath <bbros>\gfx`, путь сдвоится
  и png молча улетит в `<bbros>\gfx\gfx\` — мод соберётся со СТАРЫМ png (копия идёт из
  `<bbros>\gfx`). От cwd не зависит.
- Запрещено запускать фоновых агентов (background agents) — работаем строго последовательно:
  один агент за раз, дожидаемся результата. Фоновые агенты на текущий момент нестабильны
  (отвалы по таймауту).
- **Инструменты не должны мусорить в репозитории.** Временные файлы, кэши и профили —
  только вне репо (tmp/каталог инструмента вне git). Урок: браузерная автоматизация
  (Edge/WebView2 через MCP) при открытии `tools/sprite_editor.html` поднимала профили
  (`_prof_<pid>`, `_pp_<pid>`, `_smoke_profile`) прямо в `tools/` — туда попали полные
  юзер-профили Edge (~34 МБ), и IDE-стейджинг тут же подхватил ~800 файлов в git.
  Паттерны добавлены в `.gitignore`; перед `git add -A`/коммитом из IDE проверять
  `git status` на постороннее.

## Соглашения по коду и гиту

- Лог игры: `C:\Users\Ivan\Documents\Battle Brothers\log.html` (logInfo-маркеры модов, ошибки загрузки/хуков). Смотреть только по необходимости — файл большой, рутинно в него не лезем.

- **Не хукать то, что можно переопределить внутри мода.** Если тип сущности описан в самом моде — меняй его файл, а не вешай глобальный классовый хук на ванильный класс: хук бьёт по ВСЕМ типам игры и дороже. Паттерн — override в файле сущности с ранним return и вызовом родителя (как ванильный `scripts/entity/tactical/humans/nomad_archer.nut` для `onOtherActorDeath`/`onOtherActorFleeing`). Хук на чужой класс — только когда правка должна затронуть ванильные/чужие типы. Пример: смерть крысиных стай не понижает мораль скавенам — переопределение `onOtherActorDeath` в файлах сущностей скавенов (мод Skaven), а не хук `scripts/entity/tactical/actor`.
- Формат/стиль — как в соседних файлах мода-референса. Минимальные изменения.
- Запрещено менять порядок существующих записей в реестрах-конфигах (сейвы) — новое в конец.
- После правок .nut — чекер баланса скобок/строк `tools/nut_check.py`.
- Ассеты (*.png, *.ogg, *.wav, *.brush) в гит не коммитятся (см. .gitignore) — они локальные;
  `.brush` — текстовые описатели спрайтов, при необходимости переносимых на другую машину стоит рассмотреть коммит.
- git-мутации (commit/push) — только по явной просьбе.
